# MAX: автоматическая подготовка постов

Конвейер: **Не готовы → Отсортирован → Отфильтрован → Маркировка → На публикацию**.
Последняя стадия — `ready`. Сервис ничего не отправляет в каналы.

## Что запускается

`deploy/publisher.compose.yaml` содержит web, два отдельных worker моделей,
collector и pipeline-coordinator. Образы собираются в CI, сервер получает их по digest.
Coordinator не импортирует inference и не загружает веса. Его лимиты — 256 МБ,
0,25 CPU; один пул из одного соединения, без overflow. Он проверяет до 20 карточек
раз в две секунды. Применение изменённых фильтров также выполняется этим процессом,
а не web. Пулы всех пяти служб ограничены суммарно восемью подключениями
при лимите роли publisher в десять. Worker имеют собственные пулы; задания лежат в PostgreSQL.

Collector получает `COLLECTOR_MODE=new_only`. `AUTO_PUBLISH`, внешние LLM,
комментарии и `COLLECTOR_PROCESS_SAVED_POSTS` выключены. Недельный импорт и CLI
полной истории сохраняются как отдельные действия, автоматически не запускаются.

## Граница сбора и перезапуск

В `service_runtime.started_at` для collector сохраняется момент первого включения.
Начальные чаты MAX получают его в `telegram_sync_state.live_since`. Новый чат —
момент обнаружения. Повторный запуск сохраняет эти значения; повторно добавленный
в папку чат получает новую границу. Записи не удаляются после выхода чата из папки.

`reconciled_message_id` — только полностью завершённый обход. Realtime сохраняет
пост и карточку, но не двигает этот курсор. Поэтому более позднее realtime-событие
не закрывает пропущенный диапазон. Сверка идёт раз в 300 секунд. Сбой оставляет
старый курсор; повтор использует уникальность `(chat_peer_id, message_id)`.
FloodWait ждёт указанное Telegram время. Ошибка чата не останавливает остальные.

Collector учитывает изменения и удаления известных постов. Неизвестный старый
пост не импортируется из-за редактирования. Загрузки медиа ограничены двумя;
предел файла — 100 МБ. Временные файлы удаляются, завершённые переименовываются.
Ошибки записи не перескакивают курсор сверки. Файл сессии, ключи и сырые тексты
не входят в Git. Healthcheck проверяет heartbeat и завершённую сверку по маленькому атомарному
JSON-снимку успешной записи состояния в БД. Новое подключение для этой проверки
не создаётся. После перезапуска снимок заново записывает живой цикл.

## Карточки, модели и фильтры

Миграция `0014_live_automation` по умолчанию устанавливает `auto_enabled=false`.
В автоматике участвуют новые карточки и явно отобранные/вручную маркированные.
Одноразовый `deploy/bootstrap_automation.py` включает только согласованные 13
отобранных и одну маркированную; 6021 старую карточку он не запускает.

Координатор определяет модели по активным неархивным фильтрам. Сначала TF-IDF,
затем MiniLM, если она нужна. Для одной карточки не выполняются два задания
одновременно. Ручные прогоны обеих моделей остаются доступны и сохраняются в БД.
Пост без текста получает «Только медиа» или «Пустой», без semantic inference.

Оценки проверяются по версии таксономии и отпечатку текста. Отсутствие результата
не равно нулю. Совпадения назначают пользовательские лейблы из словаря. Лейблы
постоянные, с историей основания; чтение доски их не назначает. Без совпадения
пост остаётся в «Отсортирован». Для автоматического продвижения сохранённого
лейбла недостаточно: нужно актуальное совпадение действующего фильтра.

## Источник, вложения и готовность

`app/content/post_preparation.py` — общий код автоматической маркировки и кнопки
«Источник →». Оригинал хранится в `telegram_posts.text`, копия с источником —
в `pipeline_entries.marked_text`. Поля `marked_source_url`, `marked_text_sha256`,
`marked_at` фиксируют ссылку, вход и время. Повтор не дописывает вторую ссылку.

При переходе в `ready` проверяются актуальность маркировки, ссылка и файлы всех
известных членов альбома. Короткое ожидание альбома защищает от неполной группы
realtime-событий. Поздний член альбома отзывает готовность для повторной проверки.
`ready_at` и `last_operation_at` сохраняют времена переходов. Классификация и
назначение лейблов имеют свои timestamps в существующих таблицах.

Слишком большой, отсутствующий или не скачанный файл блокирует готовность.
Карточка показывает конкретную причину. «Повторить подготовку →» доступно только
остановленной карточке; оно также запрашивает повтор загрузки известного файла.
Бесконечной подстановки текстовой версии нет. После изменения текста маркировка
и ready отзываются, результаты становятся stale, автоматическая карточка
пересчитывается. Удаление источника останавливает её.

## Ошибки и интерфейс

Переходы выполняются отдельными транзакциями под блокировкой карточки. Для
временных ошибок — три повтора через 10, 30 и 120 секунд, затем `stopped`.
Невыполнимые условия дают `blocked` сразу. Поля `auto_phase`, `auto_attempts`,
`auto_retry_at`, `last_error` хранят состояние между перезапусками.

Защищённые API:

- `GET /api/pipeline/board-fragment` — те же отборы, колонки и счётчики, что у доски.
- `GET /api/pipeline/board-state` — состояния карточек, моделей и автоматики.
- `POST /api/pipeline/{id}/automation/retry` — явный повтор остановленной карточки.
- `POST /api/pipeline/{id}/mark-source` — ручное выполнение общего шага источника.

Доска опрашивается раз в пять секунд на видимой вкладке. Сохраняются URL отбора,
прокрутка страницы и доски. Во время ручного запроса обновление не заменяет карточку.
Dashboard показывает пять стадий, живые циклы, очередь и число остановленных.
Nginx Basic Auth сохраняется. Ответы доски не являются командами обработки.

## Проверка и откат

Тесты `test_automation_integration.py` выполняются только в disposable PostgreSQL
с именем `publisher_filter_qa*`. Проверяются курсоры, границы, FloodWait, обе модели,
пустые посты, отсутствие совпадения, ready, редактирование, удаление, вложения,
права API и повтор. Существующие проверки медиа и фильтров продолжают выполняться.
Тестовые сообщения в реальные чаты не отправляются.

До смены релиза сохраняются прежние image digest и compose/env с правами 600.
Сначала миграция и web/workers, затем bootstrap и coordinator. Collector включается
последним. При откате collector/coordinator останавливаются; возвращаются прежние
образы и конфигурация. Данные сохраняются, схему назад не понижаем. Не запускать
старый collector в режиме недельной догрузки при откате.
