# MAX: корпус, модели, отбор и доставка

Telegram здесь только источник. Источник — пользовательская папка `MAX`, доставка — девять каналов MAX. Старые drafts, рерайт и Telegram publisher в этот маршрут не входят.

## Что запускается

```mermaid
flowchart LR
    TG[Папка MAX в Telegram] --> COL[collector: new_only]
    COL --> DB[(PostgreSQL)]
    DB --> CO[coordinator]
    CO --> ML[TF-IDF / MiniLM: inference]
    ML --> FL[Действующие фильтры]
    FL --> LAB[Лейблы словаря]
    LAB --> SRC[Маркировка источника]
    SRC --> RDY[На публикацию]
    RDY --> OUT[Outbox в PostgreSQL]
    OUT --> SEND[publication-worker]
    SEND --> MAX[Канал MAX]
    MAX --> CHECK[Чтение и сверка]
    CHECK --> HIST[История доставок]
```

Collector сохраняет новую карточку, coordinator доводит её до `ready`. Сам лейбл не даёт разрешение на отправку: нужны актуальные текст, результат проверенной модели и совпадение действующей версии фильтра. Отправитель не загружает модели.

В compose у отправителя один слот подключения БД, 256 MiB RAM и 0,25 CPU. У него отдельный `MAX_PUBLISHER_ENABLED`. Общий старый `AUTO_PUBLISH` остаётся `false`. Автоматический сбор старого буфера не включается.

## Где лежит корпус

Тексты, ручная разметка, SQLite и приватные ошибки моделей хранятся **вне checkout**. В Git идут инструменты и тесты, но не корпус, session-файл или ключ. Рабочая VPS хранит исходные сообщения и inference-результаты; обучение на ней не запускается.

Историческая выгрузка на время ограниченной партии останавливает collector под отдельной блокировкой. Второй процесс не открывает тот же файл Telethon-сессии. Курсор обучения и постоянная граница `new_only` — разные вещи. После партии collector запускается снова; `FloodWait` сохраняется между запусками выгрузки.

Codex читает текст и явно задаёт `yes`, `no` или `unclear`. Скрипт разворачивает эти уже заданные метки, проверяет формат и сохраняет партию. Он не угадывает смысл по ключевому слову, источнику или соседнему посту. Точное повторение текста имеет одну разметку. Близкие варианты читаются отдельно и связываются для разделения выборок.

Пустая подпись не идёт в смысловой inference. Короткая конкретная подпись пригодна; «смотрите что получилось» без содержимого — нет. Изображения, OCR, видео и звук не определяют тему. Рекламный футер канала не заменяет тему сообщения.

Восемь новых тематических признаков и `is_joke` — это условия модели. `caption_has_context` отдельно описывает достаточность подписи. Пользовательский лейбл из словаря остаётся отдельной записью с постоянным ID.

## Проверка обучения

До фиксации dataset нужны 1000 положительных train-текстов на каждую из девяти тем. Validation, test и отрицательные примеры идут сверх квоты. `unclear` маскируется, а не превращается в отрицательный ответ. Старая контрольная сотня и её найденные близкие варианты принудительно остаются в test.

Группировка использует приближённый поиск похожих текстов. Это защита от найденных повторов, а не доказательство отсутствия всех возможных парафразов. Спорные, редкие и случайные обычные тексты перепроверяются без показа старых ответов. Старые метки допускаются лишь после отдельного сохранённого аудита.

TF-IDF и MiniLM используют одни и те же метки и группы. Эпоха MiniLM, калибровка, модель маршрута и пороги выбираются на validation. После этого test проверяет уже зафиксированное решение. Отчёт измеряет **согласие с Codex**, а не независимую человеческую точность.

Для включения маршрута требуются минимум 50 отложенных совпавших примеров и минимум 90% корректных назначений. Отдельно сохраняются ошибки по признакам, коротким подписям и каналам-источникам. Недобор не скрывается: соответствующий маршрут не включается.

Manifest содержит dataset SHA, веса и вспомогательные файлы модели. Версия учитывает веса, калибровку, taxonomy и tokenizer. Изменившийся файл не может загрузиться с прежней подтверждённой версией.

## Подключение маршрутов

`scripts/install_channel_routes.py <bundle>` проверяет артефакт и показывает будущие пороги. `--commit` переносит их в БД. Каталог runtime должен совпасть с taxonomy из проверенного артефакта. Текущий фильтр «Смешное» получает новую версию; история прежней версии сохраняется.

Скрипт не создаёт задания массового пересчёта старого буфера, доставки или переключатель автоматической публикации. Ключ бота ему не передаётся. Не прошедший тесты отчёт и изменившиеся веса импортировать нельзя.

## Настройки и секрет

| Настройка | Назначение |
|---|---|
| `MAX_PUBLISHER_ENABLED` | Разрешает работу отдельного отправителя |
| `MAX_BOT_TOKEN_FILE` | Путь к файлу ключа, смонтированному только в отправитель |
| `AUTO_PUBLISH=false` | Старый механизм публикации не запускается |
| `DB_POOL_SIZE=1`, `DB_MAX_OVERFLOW=0` | Пул процесса отправителя |
| `MEDIA_DIR` | Сохранённые вложения, только чтение для отправителя |
| `MaxPublicationControl.enabled_since` | Постоянная граница включения публикации новых постов |

На Linux файл ключа должен иметь права `600`. Ключ не передаётся web, моделям, URL, Git или браузеру. Перед выпуском нужно убрать прежний `MAX_BOT_TOKEN` из общего env, если он там есть.

Авторизация существующего сайта сохраняется. `/publication` и `/api/publication/*` закрыты; изменяющие запросы проверяют происхождение. В ответах нет upload-токенов или содержимого секрета.

## Первая партия и дальнейшая работа

1. Бот должен состоять во всех девяти каналах и иметь публикацию и чтение. Отправитель проверяет членство и историю. Управление участниками и каналом ему не требуется.
2. Codex читает выбранные карточки: тема, актуальность, источник и вложения. Для первой партии выбираются ровно 20 новых публикаций на канал, каждая помещается в одну публикацию MAX.
3. Предпросмотр `/api/publication/batches/preview` возвращает оригинальный текст, источник, число вложений и отпечаток. Найденные в истории и очереди повторы не принимаются.
4. `/freeze` сохраняет конечный список 180 проверенных карточек. `/start` заново проверяет отпечатки и ставит всю партию в очередь одной транзакцией. Ошибка одной карточки не оставляет незаметно частичную новую очередь.
5. MID сохраняется до сетевого чтения результата. Доставка завершена только после сверки всех частей. Повтор процесса читает сохранённый MID, а не отправляет сообщение снова.
6. После 180 подтверждённых доставок `/automatic` сохраняет границу включения. Только карточки и сообщения после неё попадают в автоматическую очередь. Старый невыбранный буфер остаётся на месте.

Один источник может иметь доставки в несколько каналов. Внутри канала источник и содержимое защищены отдельными уникальными ограничениями. Уже доставленная часть не пересылается повторно. После изменения источника показывается расхождение; новая копия уже опубликованного поста не создаётся.

## Текст, файлы и ошибки

Оригинал не переписывается. Скрытые Telegram-ссылки сохраняются отдельным списком, источник добавляется отдельно. Текст разбивается без удаления символов; в расчёте лимита используется консервативный UTF-16. Последующие части связаны ответами.

Вложения проходят проверку файла и SHA. Для MAX учитываются пределы форматов: визуальные вложения группируются до 12, аудио и файлы отправляются отдельными частями. Несовместимый файл не выбрасывается молча. Удалённая часть альбома или недоступный файл блокируют отправку. На канал отправляется не больше одного сообщения в секунду.

Подтверждённый отказ MAX можно повторить с ограниченными задержками. Таймаут после начала POST означает `unknown`, поскольку сообщение могло быть принято. Сначала читается канал. Повтор разрешается только после доказанной недоставки и явного подтверждения владельца. Для автоматического узнавания неопределённого вложения нужен постоянный ID, а не совпадение количества картинок.

MAX меняет временные токены изображений при чтении. Сверка не принимает это изменение за потерю файла. История читается с перекрытием временной границы страницы, чтобы не пропустить сообщения с одной миллисекундой; неоднозначная страница останавливает проверку.

## Проверки и выпуск

Тесты используют отдельную disposable PostgreSQL БД и транспорт MAX только внутри test-fixture. Рабочий runtime не содержит демонстрационного отправителя. Проверяются схема, авторизация, оригинал, Unicode, повторы, разные маршруты, перезапуск, неопределённая отправка, история и изменение источника.

После локальных проверок запускается `Portfolio validation` в GitHub Actions. Закреплённые образы собираются вне VPS. Сам workflow не содержит SSH-деплоя или очистки чужих Docker-ресурсов.

Выпуск требует отдельной проверки VPS: p95 inference до двух секунд, доступная RAM не меньше 1,5 GiB, диск не меньше 30 GiB, отсутствие OOM. Сначала применяются миграция, модели и приложение; sender до проверки остаётся выключенным. Следом проверяются интерфейс, членство, партия, чтение доставок и естественный новый подходящий пост.

Откат выключает отправитель и возвращает предыдущие образы, model-dir и активные версии фильтров. Корпус, результаты и история доставок не удаляются; схему назад не понижаем.
